<objective>
Make multi-page/folder profiles navigate host-side and repaint correctly (PROFILE-02). Two jobs:
(1) the structural extension - add a page-scoped `repaintPage(pageId)` to the control service that
resolves `"root"` -> `Profile::keys` else `Profile::pages[pageId].keys` and paints that page's
bound keys (fixing the Phase-14 repaint path which iterates only `Profile::keys` and would show
the wrong page on a child-folder switch); (2) a thin page-navigation owner that consumes the
Phase-15 `pageNavRequested(±1)` intent, advances a carousel over the profile's ordered top-level
pages, and calls `repaintPage(currentPageId)`. Vertical folder nesting continues to use
`OpenFolder`/`BackToParent` on the reused `ActionEngine`.

Purpose: Closes RESEARCH gap d (nobody consumes `pageNavRequested`; nothing maps a page switch
back to a repaint) and the structural Pitfall 1 (repainting `Profile::keys` on a page switch
shows the root, not the child). No device page opcode is invented - `STP` page-magic is
legacy-only; page navigation is host-side (LOCKED + PROFILE-02).

LOCKED decisions honored here:

- Decision 2 (swipe ±1 semantics): prev/next over an ORDERED FLAT LIST of the profile's
  top-level pages (a "pages carousel"); OpenFolder/BackToParent remain for vertical folder
  nesting. If the profile has only the root page, swipe is a no-op. Page switch repaints via
  repaintPage.
- Decision 4 (page-state owner): reuse the Phase-15 input service's ActionEngine as the single
  page-state authority (it consumes input and owns the nav stack); the page-nav owner reads
  currentPageId() and calls the control service repaintPage.

Output: extended `stream_dock_control_service.{hpp,cpp}` (repaintPage), Application wiring of the
page-nav owner + pageNavRequested -> repaintPage, and a MockTransport unit test (child-page
repaint + carousel switch + single-root no-op) that is the hardware-free gating proof (physical
swipe witness is Phase 25).
</objective>
