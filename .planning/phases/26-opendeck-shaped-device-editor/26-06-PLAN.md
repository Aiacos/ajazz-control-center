<objective>
Ship per-SKU layout JSON files for ALL in-scope LCD-key SKUs and the
vendor-photo attribution README. Order: AKP05E FIRST (so the operator
can immediately re-walk Phase 25 25-UAT.md Tests 1 + 6 on the live demo
unit once Plan 26-04's DeviceView lands), then the rest of the AKP05
family (akp05 provisional + mirabox_n4), then AKP153 family (5 entries),
then AKP03 family (5 entries), then Mirabox N3/N3E variants (4 entries).
AKP815 deliberately has NO layout JSON (D-13 sentinel; outline-frame
fallback continues to render it functionally even without a photo).

Per PATTERNS.md "resources/device-photos/<codename>.png" finding: this
plan does NOT create a parallel `resources/device-photos/` directory.
The existing `resources/devices/products/product-<codename>.png` photos
are REUSED. The layout JSON `photo` field references the existing photo
by name (e.g. `"photo": "product-akp05e.png"`). For SKUs that lack a
product photo in the existing directory (e.g. `akp153e_v2`,
`akp03_legacy`, `mirabox_n3en`), the layout JSON either references the
closest analog photo (e.g. `akp153e_v2` reuses `product-akp153.png`) OR
omits the `photo` field so DeviceView falls back to the outline frame
(D-07).

Each layout JSON declares:

- `codename`: machine codename matching the descriptor row.
- `photo`: existing product-\<…>.png filename (or absent for outline
  fallback).
- `viewBox`: `{w, h}` in arbitrary integer units; cells are positioned
  in this coordinate space and uniformly scaled at render.
- `keys[]`: array of `{i, x, y, w, h}` per LCD key (i 1-indexed).
- `encoders[]`: array of `{i, x, y, w, h}` per encoder (i 0-indexed),
  empty when `encoderCount == 0`.
- `touchZones[]`: array of `{i, x, y, w, h}` per touch zone (i
  0-indexed), empty when `touchZoneCount == 0`.

This plan runs in parallel with Plan 26-05 (different files; no
overlap). Both depend on Plan 26-04 (the DeviceView consumer of these
JSONs + the CMake glob registration).

Cell-position coordinates are derived in two steps:

1. Use the EXISTING product photo aspect ratio to pick the viewBox
   (e.g. 600×400 for landscape AKP05E; 400×600 for portrait AKP815-ish).
1. Estimate cell positions by overlaying a grid mentally on the photo,
   pinning corner offsets to the photo's bezel. Exact pixel-precision
   is NOT required for v1 — the editor still functions if cells are
   slightly off-photo; visual polish is a follow-up. The KEY thing is
   that the cells correspond geometrically to the device's real
   layout (AKP05E's 2 rows of 5 keys, then 4 dials below, then 4
   touch zones at the bottom).
   </objective>
