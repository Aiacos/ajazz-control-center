# Phase 32 — UI Design Contract

> Visual and interaction contract for the Phase 32 frontend surface only: the
> scrollable device-view editor (EDIT-01). Generated by gsd-ui-researcher,
> verified by gsd-ui-checker.
>
> **Scope is contained.** This phase wraps the existing device grid in a
> vertical `ScrollView` so oversized SKU grids scroll. It does NOT redesign the
> editor, introduce new panels/theming/controls, or touch the
> key/encoder/touch delegate visuals. The Multi/Toggle dispatch and willAppear
> wire fix are backend (excluded here) except for one render expectation noted
> below. This is a Qt 6 / QML app, not a web/shadcn project — design-system,
> color, and copywriting sections record the EXISTING project tokens this scroll
> wrapper must reuse (it introduces none of its own).

## Frontend Change Contract (EDIT-01)

### What wraps what

Current chassis structure (`src/app/qml/DeviceView.qml`):

```
RowLayout
└─ ColumnLayout (left/center)
   └─ FocusScope#chassisScope  (Layout.fillWidth/fillHeight)
      └─ Item#chassisArea  (anchors.fill: parent)
         ├─ Image#chassisPhoto      (photo background, anchors.fill)
         ├─ DeviceCanvas#deviceCanvas  (anchors.fill — the grid lives here)
         ├─ RoundButton#trashBtn    (top-right overlay)
         └─ EmptyState              (centered overlay)
```

`DeviceCanvas` (`src/app/qml/components/DeviceCanvas.qml`) is a content-sized
`Item` whose `frame` Rectangle is `anchors.centerIn: parent` and sized to its
`ColumnLayout#body` (`body.implicitWidth/Height + 2*spacingXl`). The three lanes
(key Grid, TouchStripLane, dial Row) stack vertically inside `frame`. When the
SKU geometry is large, `frame` grows taller than the available `chassisArea` and
currently **clips / overflows** because nothing scrolls.

### Required wrapping

Wrap the **grid surface (`DeviceCanvas`) in a vertical `ScrollView`** inside
`chassisArea`. Target structure:

```
Item#chassisArea  (anchors.fill: parent)
├─ Image#chassisPhoto                          (UNCHANGED — stays full-area bg)
├─ ScrollView#deviceCanvasScroll               (NEW — anchors.fill, margins: Theme.spacingMd)
│  └─ DeviceCanvas#deviceCanvas                 (MOVED inside; see content sizing)
├─ RoundButton#trashBtn                         (UNCHANGED — stays anchored overlay, NOT inside the scroll)
└─ EmptyState                                   (UNCHANGED — centered overlay)
```

Contract rules:

1. **The `ScrollView` replaces `DeviceCanvas`'s former `anchors.fill` role.** The
   `ScrollView` fills `chassisArea` (minus `Theme.spacingMd` margins, matching
   the canvas's previous margins at `DeviceView.qml:340`). `DeviceCanvas` becomes
   the ScrollView's content item.
1. **`trashBtn` and `EmptyState` stay as overlays of `chassisArea`** — siblings of
   the `ScrollView`, NOT children of it. The trash zone must remain pinned
   top-right and visible regardless of scroll position; it is a fixed
   drag-target, not scrolling content.
1. **The photo background (`chassisPhoto`) stays a full-area sibling** behind the
   `ScrollView`. (It is currently mutually-exclusive with the canvas via
   `visible: !chassisPhoto.visible` — preserve that binding on `DeviceCanvas`
   inside the ScrollView.)

### Content sizing (vertical-only scroll)

- The `ScrollView` content (`DeviceCanvas`) MUST be **width-constrained to the
  viewport** so no horizontal scroll is ever produced: set the canvas
  `width: deviceCanvasScroll.availableWidth` (or
  `implicitWidth: availableWidth`), and let its height be its natural content
  height so the vertical scrollbar engages when content exceeds the viewport.
- `DeviceCanvas` centers its `frame` in its own area; keep that behavior. The
  scrollable extent is the canvas's natural (content) height. When the device
  frame is shorter than the viewport, it stays centered and does not scroll.
- **`ScrollBar.horizontal.policy: ScrollBar.AlwaysOff`** — horizontal scrolling
  is forbidden. Vertical only.
- **`ScrollBar.vertical.policy: ScrollBar.AsNeeded`** — the vertical scrollbar
  appears only when content overflows.
- `clip: true` on the `ScrollView` so overflow content is clipped to the viewport
  (not painted over the Inspector/KeyBindingList below).

### Overflow threshold (visual meaning of "scrollable")

The grid is considered **overflowing** — and therefore the vertical scrollbar
becomes reachable — when the device geometry exceeds OpenDeck's overflow rules:

> **`keyColumns > 8` OR (rowCount > 4)**, where
> **`rowCount = keyRowsResolved + (encoderCount > 0 ? 1 : 0) + (touchZoneCount > 0 ? 1 : 0)`**

i.e. the 4-row threshold counts the encoder lane row and the touch-zone lane row,
not just key rows (per EDIT-01 wording and `32-CONTEXT.md` Area 3).

- This is a **descriptor-geometry rule**, not a pixel measurement. The executor
  MAY expose it as a readonly helper on `DeviceView` (e.g.
  `_gridOverflows`) computed from `keyRowsResolved`, `_keyColumnsResolved`,
  `encoderCount`, `touchZoneCount` — useful for tests and as an explicit contract
  anchor. Whether the scrollbar actually paints is ultimately driven by
  content-height-vs-viewport (`AsNeeded`); the geometry rule is the
  spec-level acceptance predicate.
- **At or below threshold** (`columns <= 8` AND `rowCount <= 4`): no vertical
  scrollbar visible, content fits, frame stays centered.
- **Above threshold**: vertical scrollbar reachable; user can scroll the grid
  vertically; horizontal scroll never available.

### Delegate distinctness (preserved, not redesigned)

The three controllers stay VISUALLY and FUNCTIONALLY distinct — the existing
delegate types are unchanged. The spec preserves the current differentiation:

| Controller   | Delegate                         | Visual identity (existing, unchanged)                                                     | Functional identity                                    |
| ------------ | -------------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| Key          | `KeyCell`                        | Square LCD tile (76×76, `_keyCell`), icon + label, drop target                            | `keyClicked` / `keySwapRequested` / `keyActionDropped` |
| Encoder dial | `EncoderDial` (in dial Row lane) | Circular dial (64×64) in an equal-width slot under each zone                              | `encoderClicked` / `encoderSwapRequested`              |
| Touch zone   | `TouchStripLane` zones           | Horizontal strip divided into `touchZoneCount` zones, spanning the key-grid content width | `zoneClicked` / `zoneSwapRequested`                    |

Do **not** merge these into a unified cell. The ScrollView wraps all three lanes
together (they live in one `DeviceCanvas#frame`); the wrapping is purely
container-level and changes none of the delegate shapes, sizes, or signals.

### Render expectation from backend Toggle Action (BIND-07)

Not a new control. When a Toggle Action cycles `currentState`, the bound key's
on-screen face re-renders `instance.states[currentState]` (imagePath/title). The
existing live-render mirror already handles this: `StreamDockControlService`
emits `keyImageAssigned(keyIndex, revision)` and `DeviceView.qml:88-104` repoints
the cell `iconSource` at `image://livekey/<idx>?r=<rev>`. **No UI work is
required** for per-state re-render beyond confirming the cell mirrors the live
frame after a state change — record it as a render expectation, not a task.

## Debug-Addressability Contract (DOD — CLAUDE.md)

Every new interactive container MUST be debug-addressable via `objectName`
(`findByName`). The scroll container is the only new addressable element.

| objectName           | Element              | Readable via `scripts/ajazz-debug qml.get <objectName>`                                                                                                                                                                          |
| -------------------- | -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `deviceCanvasScroll` | the new `ScrollView` | `ScrollBar.vertical.position` (0.0–1.0 scroll fraction), `ScrollBar.vertical.size` (visible fraction; `< 1.0` ⇔ scrollable), `ScrollBar.vertical.policy`, `ScrollBar.horizontal.policy`, `contentHeight`, `contentItem.contentY` |

Requirements:

- `objectName: "deviceCanvasScroll"` on the new `ScrollView`.
- The vertical `ScrollBar`'s `position` and `size` MUST be readable so a test can
  assert both *that* a SKU overflows (`size < 1.0`) and *where* it is scrolled
  (`position`). `qml.get deviceCanvasScroll` must return scroll-position
  properties (success criterion 5 in `32-CONTEXT.md`).
- If `ScrollBar.vertical.position` is not directly reachable through `qml.get` on
  the ScrollView in this harness, ALSO expose the underlying
  `Flickable.contentY` by giving the ScrollView's `contentItem` an `objectName`
  (e.g. `deviceCanvasFlick`) so `qml.get deviceCanvasFlick` returns `contentY`
  and `contentHeight`. Provide at least one machine-readable scroll-position
  surface; both is preferable.

## Acceptance Criteria (debug-channel-checkable)

All phrased as assertions drivable from `scripts/ajazz-debug` against a running
app (`AJAZZ_DEBUG_CONTROL=1`). ctest green is necessary but NOT sufficient
(CLAUDE.md debug-channel rule) — these MUST be verified live.

1. **Scroll container is addressable.**
   `qml.get deviceCanvasScroll` returns an object including
   `ScrollBar.vertical.position`, `ScrollBar.vertical.size`,
   `ScrollBar.horizontal.policy`, and `contentHeight` (or the companion
   `qml.get deviceCanvasFlick` returns `contentY` + `contentHeight`).

1. **Over-threshold SKU is scrollable.** With a device whose geometry exceeds the
   rule (`columns > 8` OR `keyRows + encoderRow + touchRow > 4`) active
   (e.g. drive `device.setActiveDevice` to such a SKU, or
   `device.renderTest` with an over-threshold geometry):
   `qml.get deviceCanvasScroll` reports `ScrollBar.vertical.size < 1.0` (content
   exceeds viewport ⇒ vertical scrollbar present). A `screenshot` shows a
   vertical scrollbar in the chassis area.

1. **Under-threshold SKU is NOT scrollable.** With a device at/under threshold
   (e.g. a 3×3 AKP05-class grid): `qml.get deviceCanvasScroll` reports
   `ScrollBar.vertical.size >= 1.0` (or no vertical scrollbar). `screenshot`
   shows no vertical scrollbar; the frame stays centered.

1. **No horizontal scroll, ever.** `qml.get deviceCanvasScroll` reports
   `ScrollBar.horizontal.policy == ScrollBar.AlwaysOff` (or equivalent), and on an
   over-threshold SKU the content width never exceeds the viewport width
   (no horizontal scrollbar in `screenshot`).

1. **Scroll position is readable + changes.** After programmatically scrolling
   (set `contentY` / `ScrollBar.vertical.position` via `qml.set`, or scroll
   interaction), `qml.get` reflects the new position (non-zero `position` /
   `contentY`).

1. **Delegates remain distinct.** On an active SKU with all three controller
   types, `screenshot` shows square key tiles, a horizontal touch strip, and
   circular dials as three distinct lanes; key/encoder/zone selection still route
   through their respective signals (`keyClicked`/`encoderClicked`/`zoneClicked`
   — verifiable by selecting each and reading `selectedKeyIndex` /
   `selectedEncoderIndex` / `selectedZoneIndex` via `qml.get` on `DeviceView`).

1. **Trash zone stays pinned.** After scrolling, `screenshot` shows `trashBtn`
   still anchored top-right of the chassis (not scrolled away with the grid).

1. **Toggle render mirror (render expectation, backend-driven).** After a Toggle
   Action state cycle (synthetic `input.key`), the bound key's on-screen face
   updates to `states[currentState]` — confirmed via `screenshot` (existing
   `keyImageAssigned` mirror; no UI work, just confirm it still fires through the
   wrapped canvas).

## Qt 6 / QML implementation notes (from CLAUDE.md gotchas)

- **`ScrollView` content sizing:** constrain the content item width to
  `availableWidth` to prevent the implicit horizontal scroll Qt would otherwise
  create from a content item wider than the viewport. This is the canonical
  vertical-only ScrollView pattern.
- **`objectName` mandatory:** the new `ScrollView` (and, if used, its
  `contentItem` Flickable) MUST set `objectName` — un-named controls are
  invisible to `qml.get/set` (CLAUDE.md debug-addressability rule).
- **Overlays outside the scroll:** keep `trashBtn` and `EmptyState` as
  `chassisArea` children (siblings of the ScrollView). Material attached
  properties / fixed overlays must not be parented into scrolling content.
- **Do not redeclare `index`** on `KeyCell`/dial delegates (existing
  duplicate-property trap, see `DeviceCanvas.qml:108-109`) — the wrapper touches
  none of these delegates, so leave them untouched.
